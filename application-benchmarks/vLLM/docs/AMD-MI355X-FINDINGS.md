8192→1024 still gains from the extra load. 1024→8192 loses throughput at vLLM's default CUDA-graph capture limit (`max_cudagraph_capture_size` = 512, from `serve.log`): its steps are decode, and decode batches above the limit run without full CUDA graphs. They also run a vLLM **nightly** (`vllm/vllm-openai-rocm:nightly-d9105ea8001e0a6d77a96327d17515bb5791fb36`, contained in v0.30.0) with flags our spec does not use or does not allow: no `--max-model-len` / `--max-num-batched-tokens` (fixed at 9216 here, §8.1), `--moe-backend aiter` with shared-expert fusion, `FULL_AND_PIECEWISE` CUDA graphs, `--async-scheduling`, and `VLLM_ROCM_QUICK_REDUCE_QUANTIZATION=INT4` (an INT4-quantised all-reduce, additional activation quantisation under §8.5).

### The KV pool gap is not a capacity difference

SemiAnalysis report 4,386,107 KV tokens for this shape against our 300,533. Both are the same vLLM log line, `GPU KV cache size: N tokens`, and vLLM computes it as `max_concurrency × max_model_len` (`get_kv_cache_capacity`, `vllm/v1/core/kv_cache_utils.py`). Their serve command sets no `--max-model-len`, so it is DeepSeek-V4's default of 1,048,576: 4,386,107 = 4.18 × 1,048,576. Ours is 32.61 × 9,216. The two figures measure the same pool at different request lengths and do not compare.

Neither is the real ceiling either. `max_concurrency` is a worst-case reservation summed over DeepSeek-V4's many KV groups (compressed MLA at ratios 4 and 128, indexer, compressor state, 128-token sliding window); blocks are allocated on demand at runtime. Measured on one node at N=512, 512 requests run with ~21% KV-cache usage and no preemption (troubleshooting §12.6).

Ruled out along the way: the engine version (v0.30.0 moves the reported pool 0.7%), §8.1's literal `fp8` (`auto` is byte-identical on ROCm), and DCP, which refuses to start for this model on either version (`DCP is not supported with sparse indexer KV compression (compress_ratio=4)`).

    with rocm_aiter_moe.py's own comment that mxfp6/mxfp8 are unsupported in AITER.

So which counter a MIXED FP8xFP4 MFMA increments is still open. Indirect evidence that it
runs at FP8 rate: AITER's own tuned table for the fp8xfp4 path tops out at ~2490 TFLOPS,
about half of MI355X's ~5 PFLOPS FP8 peak but only a quarter of its ~10 PFLOPS FP4 peak.
A kernel executing at FP4 rate would not be capped there.

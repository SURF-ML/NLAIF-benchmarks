All tok/s/GPU. **The two independent implementations agree to within 5.0% at every shared concurrency**, from 16 to 512.

How they reach concurrency 512 on one node: their serve command (`benchmarks/single_node/fixed_seq_len/deprecated/dsv4_fp4_mi355x_vllm.sh` in InferenceX) sets no `--max-num-seqs`, so vLLM's default for ≥160 GB GPUs, 1024, applies — they never take N from the startup capacity line. They also run a vLLM **nightly** (`vllm/vllm-openai-rocm:nightly-d9105ea8001e0a6d77a96327d17515bb5791fb36`, contained in v0.30.0) with flags our spec does not use or does not allow: no `--max-model-len` / `--max-num-batched-tokens` (fixed at 9216 here, §8.1), `--moe-backend aiter` with shared-expert fusion, `FULL_AND_PIECEWISE` CUDA graphs, `--async-scheduling`, and `VLLM_ROCM_QUICK_REDUCE_QUANTIZATION=INT4` (an INT4-quantised all-reduce, additional activation quantisation under §8.5).

### The KV pool gap is not a capacity difference

SemiAnalysis report 4,386,107 KV tokens for this shape against our 300,533. Both are the same vLLM log line, `GPU KV cache size: N tokens`, and vLLM computes it as `max_concurrency × max_model_len` (`get_kv_cache_capacity`, `vllm/v1/core/kv_cache_utils.py`). Their serve command sets no `--max-model-len`, so it is DeepSeek-V4's default of 1,048,576: 4,386,107 = 4.18 × 1,048,576. Ours is 32.61 × 9,216. The two figures measure the same pool at different request lengths and do not compare.

Neither is the real ceiling either. `max_concurrency` is a worst-case reservation summed over DeepSeek-V4's many KV groups (compressed MLA at ratios 4 and 128, indexer, compressor state, 128-token sliding window); blocks are allocated on demand at runtime. Measured on one node at N=512, 512 requests run with ~21% KV-cache usage and no preemption (troubleshooting §12.6).

Ruled out along the way: the engine version (v0.30.0 moves the reported pool 0.7%), §8.1's literal `fp8` (`auto` is byte-identical on ROCm), and DCP, which refuses to start for this model on either version (`DCP is not supported with sparse indexer KV compression (compress_ratio=4)`).

## Is the FP4 matrix path actually used?

gfx950 separates 8-bit from 4/6-bit matrix ops in hardware (`SQ_INSTS_VALU_MFMA_MOPS_F8` vs `..._F6F4`), so this is measured, not inferred. A control run confirms the counters register at all — without it a zero F6F4 would be ambiguous between "no 4-bit ops" and "collection broken".

```

path used" is measurable rather than inferred:

    SQ_INSTS_VALU_MFMA_MOPS_F6F4    4/6-bit MFMA

CONTROL — does collection work at all? (bf16 matmul + fp8 matmul, 20x 4096^3)

"counters broken". 5,368,709,120 x 512 FLOP/MOP = 2.749e12 = exactly 20 x 2 x 4096^3,
so the counters are accurate, not merely non-zero.
```
